## 2. 产品简介（复赛版 v2.8.1）

### 是什么

字帖生成器是一款**纯前端 PWA 离线应用**，基于 Vite + ES Module 工程化构建。无需服务器、无需安装、无需联网，安装到桌面/手机主屏后完全离线可用。输入汉字后自动生成带拼音标注、组词提示、笔画分解的描红字帖，支持**5 种网格类型 + 4 色线框预设 + 双轨矢量 PDF 输出**。

相比 v2.8.0，v2.8.1 聚焦于**移动端（MatePad / HarmonyOS）打印 PDF 空白问题的止血修复与配套文档建设**：

- 🐛 **MatePad 移动端打印 PDF 空白修复**：废弃 `visibility: hidden/visible` 方案，改用 `display:none` 显式隐藏 UI 元素；新增移动端断点规则保留 SVG 可见性；新增移动端 UA 检测与用户引导 toast；用 RAF 双层同步触发 `window.print()` 保持用户手势上下文
- 📱 **PWA 安装二维码 + 多平台指南**：5 平台安装步骤（HarmonyOS / Android / iOS / Windows / macOS）+ 8 项验证清单 + 8 条 FAQ + 在线二维码（api.qrserver.com 生成）
- ✅ **移动端功能测试清单**：74 项测试用例覆盖 10 大类别，"打印 PDF"章节从"待修复"更新为"已修复"，新增 TC-04-06 / TC-04-07 移动端引导与替代路径测试项
- 📊 **飞书问卷模拟提交数据**：3 套测试数据（MatePad / Android / Windows）+ Session ID + 演示视频占位符 + Markdown 表格 / 纯文本双版本
- 📚 **替代方案研究文档**：5 方案对比（用户引导 / svg2pdf.js / html2canvas / dom-to-image / Web Share）+ HarmonyOS 网页转 PDF 操作路径（3 个版本差异）+ 分阶段实施建议（v2.8.1 止血 → v2.9.0 主推 → v3.0.0 统一）

### 面向谁

- **中小学语文教师** — 快速生成课堂练习字帖，自定义练习内容

### PWA 安装与离线使用

本作品**前端核心功能**是标准的 PWA（Progressive Web App），支持安装到桌面/手机主屏，安装后**完全离线可用**（Service Worker 预缓存全部资源含字体）。**Puppeteer 矢量 PDF 功能需要本地 Node.js 服务，在线版本不可用**。

| 平台                | 浏览器                        | 安装方法                                                              |
| ----------------- | -------------------------- | ----------------------------------------------------------------- |
| **Windows**       | Edge / Chrome（推荐）          | 地址栏右侧 ⊕ 图标 → 安装；或菜单 →「将此站点作为应用安装」                                |
| **macOS**         | Chrome / Edge              | 地址栏 ⊕ 图标 → 安装                                                     |
| **Android**       | Chrome / Edge / Firefox    | 浏览器菜单（⋮）→「添加到主屏幕」或「安装应用」                                          |
| **iOS 16.4+**     | Safari                     | 分享按钮 →「添加到主屏幕」（需 iOS 16.4+ 才支持 PWA 推送和离线）                        |
| **iOS < 16.4**    | Safari                     | 「添加到主屏幕」可创建快捷方式，离线能力有限                                            |
| **Firefox 桌面版**  | 不支持 PWA 安装                 | 可正常在线使用                                                           |
| **HarmonyOS**     | 华为浏览器 / Chrome             | 浏览器菜单 →「添加到主屏幕」（v2.8.0 已修复移动端设置模态全屏遮挡问题，v2.8.1 已修复打印 PDF 空白问题） |

> [!NOTE]
> **关于 GitHub Pages 部署的说明**
>
> - GitHub Pages 是本项目当前的**在线体验入口**，主要原因是**免费、免备案、CI/CD 自动化**。
> - GitHub Pages **不支持 Node.js 后端服务**，因此在线版本只能使用浏览器打印 PDF（window.print），无法使用 Puppeteer 矢量 PDF 功能。
> - GitHub Pages 服务器位于海外，国内首次访问加载字体（~40MB）可能较慢，建议首次访问后安装 PWA 以享受 Service Worker 缓存的二次秒开体验。
> - **GitHub Pages 不是唯一发布路径**。项目源码完全开放，用户可 `git clone` 后本地运行 `npm install && npm run dev`，启动本地 Puppeteer 服务后享受完整的双轨 PDF 功能。

## 4. 产品创作历程

### 想法诞生

作为一名书法练习者，我在日常练字中遇到几个痛点：

- 市面上的字帖内容固定、无法定制
- 在线字帖工具依赖网络且常收费
- 打印出来的字帖往往是位图、放大后模糊不清
- 缺少拼音、组词、笔画分解等教学辅助信息

于是想到用前端技术，做一个**完全离线、自由定制、高清矢量输出**的字帖工具。

> 我自从用了电脑，打字技术增长，但字却越来越丑；自从练习写字之后，用小楷毛笔在 A4 复印纸上都能写出这个水平的字了：

**修复 7.1 — 移动端设置模态全屏遮挡问题（MatePad 反馈）**

- **用户反馈**：华为 MatePad（HarmonyOS）通过 GitHub Pages 访问时，设置中心切换网格类型/颜色后看似不生效
- **多 Agent 调查结论**：**不是性能滞后，也不是功能失效**。根因是 `settingsCenter.css` 移动端断点让 `.sc-modal` 全屏覆盖（100vh），重渲染发生在被遮挡的背景中，用户看不到
- **修复方案**：
  - 移动端模态改为底部抽屉（65vh，留 35vh 预览区）+ 减淡遮罩（0.5 → 0.25）
  - 字格容器添加视觉反馈（设置更新后紫色外框闪烁 400ms）

**修复 7.2 — 字数上限扩展（200 → 330 推荐 + 1000 硬上限）**

- **用户反馈**：200 字上限太少，希望增加到 330 字（30 页）
- **修复方案**：

  - 字数计数器三级样式：0-330 正常（灰色）/ 331-1000 警告（黄色）/ >1000 错误（红色）

  - **不强制截断**：用户输入超过 330 字仍可正常生成字帖，只是会输出更多页

**修复 7.3 — 打印 PDF 性能优化（GitHub Pages 慢）**

- **用户反馈**：GitHub Pages 在线版本打印 PDF 非常慢
- **多 Agent 调查结论**：
  - 首次访问慢主因：字体串行加载（40MB 跨境下载 30-60 秒）+ alert 阻塞 + waitForStrokes 10s 超时
  - 二次访问慢主因：笔画串行加载 + SVG DOM 规模（30 页 7590 SVG / 3 万节点）
- **修复方案（短期优化，预计性能提升 60-80%）**：
  - `loadFonts()` 改并行（`Promise.all`）+ `display:swap` + 按需加载（仅加载当前选中字体）
  - `printDirect()` 中的 `alert()` 改为非阻塞 toast（复用 `.puppeteer-toast` 样式）
  - `waitForStrokes` 超时从 10s 缩短为 2s（未加载的笔画自然缺失，不阻塞打印）

  - 根因 1：print.css 使用 `body * { visibility: hidden; }` + `.a4-page * { visibility: visible; }` 方案，HarmonyOS 浏览器与移动 Chrome 在 @media print 下 visibility 继承机制不可靠
  - 根因 2：pdfExport.js 用 async/await 链触发 window.print()，移动端浏览器严格要求 window.print() 在用户手势上下文内调用，async 链脱离手势上下文导致调用被吞
- **修复**：
  - [print.css](file:///c:/poem2pdf/distribution/src/styles/print.css#L77-L103) 废弃 visibility:hidden/visible 方案，改用 display:none 显式隐藏 UI 元素（共 20 个选择器）
  - [print.css](file:///c:/poem2pdf/distribution/src/styles/print.css#L124-L169) 新增 `@media print and (max-width: 900px)` 移动端断点规则，显式声明容器宽度 210mm + 保留 SVG 字格可见性
  - [pdfExport.js](file:///c:/poem2pdf/distribution/src/utils/pdfExport.js#L380-L385) 新增移动端 UA 检测（HarmonyOS/Android/iOS）
  - [pdfExport.js](file:///c:/poem2pdf/distribution/src/utils/pdfExport.js#L391-L397) 移动端显示用户引导 toast（HarmonyOS 专用提示「建议点击浏览器底部 ∷ 菜单 → 保存 PDF / WPS 网页转 PDF」）
  - [pdfExport.js](file:///c:/poem2pdf/distribution/src/utils/pdfExport.js#L409-L423) 用 requestAnimationFrame 双层同步触发 window.print()，保持用户手势上下文

> - **构建验证**：A 组代码修改完成后，由 F 组统一执行 `npm run build` 验证（839 模块，0 错误，0 警告）

> [!TIP]
> **多 Agent 协同的优势与适用场景**
>
> 1. **上下文隔离**：每个 Agent 上下文聚焦单一职责，避免在大型任务中"忘了"前面讨论的细节
> 2. **并行加速**：6 个独立任务并行执行，整体耗时 ≈ 最慢小组的耗时（而非 6 个小组耗时之和）
> 3. **可验证性**：每个小组的交付物独立可验证（A 组构建通过、B/C/D/E 组文档完整、F 组帖子覆盖所有点）
> 4. **适用场景**：当一个修复任务涉及"代码 + 多份文档"且文档间相互独立时，多 Agent 并行是最优选择

### 开发踩坑与经验

#### 踩坑 1：思源宋体 zip 解压路径不一致（v2.1）

**问题**：CI 环境下载思源宋体 zip 后，硬编码路径 `/tmp/shs/SourceHanSerifSC-Regular.otf` 找不到文件。

**排查**：实际解压路径为 `/tmp/shs/OTF/SimplifiedChinese/SourceHanSerifSC-Regular.otf`，目录结构因版本而异。

**解决**：改用 `find /tmp/shs -name "SourceHanSerifSC-Regular.otf" | head -1` 动态查找。

#### 踩坑 2：PowerShell 重定向导致 UTF-16 编码（v2.1）

**问题**：从 Git 备份分支恢复 fontManager.js 时，PowerShell `>` 重定向默认保存为 UTF-16 LE（BOM: FF-FE），Vite 报 "invalid JS syntax"。

**排查**：检查文件首 4 字节 `FF-FE-2F-00` 确认为 UTF-16 LE 编码。

**解决**：改用 .NET `[IO.File]::WriteAllText` + `UTF8Encoding($false)` 重写为 UTF-8（457,850 → 228,957 bytes）。

#### 踩坑 3：GitHub Pages 部署权限（v2.1）

**问题**：CI 构建成功但部署失败，错误 `Branch "retake" is not allowed to deploy to github-pages`。

**排查**：github-pages environment 的 deployment-branch-policies 仅允许 main 分支。

**解决**：通过 `gh api --method POST .../deployment-branch-policies -f name=retake` 添加 retake 到允许列表。

#### 踩坑 4：SVG stroke-width 在 Chrome PDF 中渲染为 0 宽度（v2.5.1）

**问题**：SVG `stroke-width=2.0`（用户单位）在 PDF 中渲染为 0 宽度（PyMuPDF 分析确认：66 条边框线 width=0.0pt）。

**根因**：Chrome PDF 引擎对 SVG stroke + `preserveAspectRatio: none` + `shape-rendering: crispEdges` 的组合处理有 bug，stroke 被转为 0 宽度填充路径。

**解决**：改用**填充矩形代替 stroke**（4 个填充矩形绘制外框，N-1 个填充矩形绘制内部竖线）。填充矩形在 PDF 中始终按精确尺寸渲染，不受 shape-rendering 和 preserveAspectRatio 影响。验证结果：边框宽度 0.92pt (0.324mm)，精确渲染。

#### 踩坑 5：CSS 压缩器丢失 .fab-settings 定位属性（v2.7.0）

**问题**：Vite 的 CSS 压缩器（Lightning CSS）在合并公共属性时，丢失了 `.fab-settings` 的 `position:fixed/top/right`。

**解决**：在 `fab.css` 添加独立定位规则 `.fab-settings{position:fixed;top:20px;right:20px;z-index:9999}`，确保构建产物中规则存在。

#### 踩坑 6：Puppeteer PDF 不应用客户端网格设置（v2.6.0，严重）

**问题**：用户切换网格类型和颜色预设后，Puppeteer 方式导出的 PDF 矢量图没有任何变化。

**根因**：Puppeteer 加载全新 dist/index.html 页面，localStorage 为空；客户端未将设置传递给服务端。

**解决**：三文件协同修复（`puppeteerClient.js` 读取并发送 → `puppeteer-server.cjs` 接收并写入 Puppeteer 页面 localStorage → `puppeteer-pdf.cjs` CLI 新增参数）。

#### 踩坑 7：多 Agent 并行开发的文件冲突（v2.1）

**问题**：多个 Agent 同时修改 main.js 和 index.html 可能导致冲突。

**解决**：Agent B 只新增文件不修改现有代码（零冲突）；Agent A 和 Agent C 顺序执行（Agent C 基于 Agent A 的结果）。

#### 踩坑 8：visibility 继承在移动端 @media print 下失效（v2.8.1，核心）

> [!WARNING]
> **v2.8.1 最关键的踩坑**
>
> **问题**：MatePad（HarmonyOS）通过 GitHub Pages 访问时，点击打印按钮后预览全空白，仅显示页眉页脚，字格区域完全空白。
>
> **根因**：`print.css` 第 78–83 行使用了 `body * { visibility: hidden; }` + `.a4-page * { visibility: visible; }` 配合方案。`visibility: hidden` 在移动端浏览器（HarmonyOS 浏览器、移动 Chrome、iOS Safari）的打印媒体下经常失效或被错误继承——某些移动浏览器会将 `.a4-page *` 的 `visible` 误判为 `inherit`，导致整页仍处于 `hidden` 状态，最终打印预览一片空白。
>
> **解决**：
> - 废弃 `visibility: hidden/visible` 方案，改用 `display:none !important` 显式隐藏 20 个 UI 选择器（`.app-header` / `.panel` / `#input-container` / `.fab-*` / `.app-sidebar` / `.quick-toolbar` / `.char-counter` / `.diff-status-bar` 等）
> - 新增 `@media print and (max-width: 900px)` 移动端断点，显式声明 `html, body { width: 210mm !important; }` + `.grid-svg-row, .grid-svg-cell, ... { visibility: visible !important; display: revert !important; }` 强制保留 SVG 字格可见性
> - `pdfExport.js` 新增 `isMobileUA` / `isHarmonyOS` UA 检测，移动端显示专用引导 toast
> - 用 `requestAnimationFrame` 双层同步触发 `window.print()`，保持用户手势上下文（移动端浏览器严格要求 `window.print()` 在用户手势内调用，async/await 链会脱离手势上下文导致调用被吞）

## 6. 技术方案分享

### 纯前端 PWA + 矢量 PDF 双轨方案

**核心理念**：零后端依赖，保护用户隐私，离线可用。

```
用户输入汉字
    ↓
pinyin-pro 转换拼音 → cnchar 组词 → hanzi-writer 笔画
    ↓
矢量 SVG 字格引擎渲染（viewBox 100×100 + CSS mm 物理尺寸）
    ↓
方案 A：window.print() → 浏览器打印预览 → 另存为 PDF（全平台，v2.8.1 修复移动端空白）
方案 B：Puppeteer 无头浏览器 → 矢量 PDF（文字可选可复制，应用网格/颜色）
    ↓
PWA Service Worker 缓存所有资源 → 离线可用
```

**技术亮点**：

- FontFace API 动态注册字体 + document.fonts.check() 验证加载
- FontFace 超时重试机制（5 秒超时 + 3 秒额外等待）
- JSON 解析三层防御（Connection:close + safeJsonParse + 请求去重）
- vite-plugin-singlefile 保留单 HTML 离线分发能力

### 矢量 SVG 字格引擎（v2.4.0 核心）

> [!IMPORTANT]
> v2.4.0 核心重构
>
> 彻底废弃 CSS 拼凑网格，重写为矢量 SVG 引擎，解决屏幕/PDF/打印三者不一致的根本问题。

```
┌─────────────────────────────────────────────────────────┐
│  矢量 SVG 字格引擎架构（GridEngine.js）                  │
├─────────────────────────────────────────────────────────┤
```

### 6.X 移动端打印 PDF 适配方案（v2.8.1 新增）

> [!IMPORTANT]
> v2.8.1 核心技术方案
>
> 本章节详细解释 MatePad 移动端打印 PDF 空白问题的根因、修复方案、HarmonyOS 浏览器「网页转 PDF」操作路径、5 方案对比以及 v2.9.0 / v3.0.0 路线图。完整研究文档见 [docs/移动端打印替代方案_v2.8.1.md](file:///c:/poem2pdf/distribution/docs/移动端打印替代方案_v2.8.1.md)。

#### 问题根因

`print.css` 第 78–83 行使用了 **`visibility: hidden / visible` 配合方案**：

```css
@media print {
  body * { visibility: hidden; }
  .a4-page, .a4-page *,
  .print-only-header, .print-only-header *,
  .print-page-section, .print-page-section * {
    visibility: visible;
  }
}
```

> [!WARNING]
> **`visibility: hidden` 在移动端浏览器（HarmonyOS 浏览器、移动 Chrome、iOS Safari）的打印媒体下经常失效或被错误继承**。该 CSS 属性保留盒模型空间，且其继承机制在不同浏览器内核下表现不一致——某些移动浏览器会将 `.a4-page *` 的 `visible` 误判为 `inherit`，导致整页仍处于 `hidden` 状态，最终打印预览一片空白。这是本问题的核心技术债。

此外，`pdfExport.js` 中通过 `async/await` 链触发 `window.print()`：

```javascript
waitForFonts().then(async () => {
    await waitForStrokes(2000);
    await new Promise(r => setTimeout(r, 300));
    window.print();  // ❌ 移动端：已脱离用户手势上下文，调用被吞
});
```

> [!WARNING]
> 移动端浏览器（Chrome 120+、HarmonyOS、iOS Safari）严格要求 `window.print()` 在**用户手势上下文内**调用。`async/await` 链会脱离手势上下文，导致调用被静默吞掉，打印对话框根本不弹出。

#### 修复方案（v2.8.1 止血）

**修复 4：requestAnimationFrame 双层同步触发**

[pdfExport.js L409-L423](file:///c:/poem2pdf/distribution/src/utils/pdfExport.js#L409-L423) 用 RAF 双层同步触发 `window.print()`：

```javascript
// v2.8.1：用 requestAnimationFrame 同步触发 window.print()
// 原因：移动端浏览器严格要求 window.print() 在用户手势上下文内调用
// async/await 链会脱离手势上下文导致调用被吞
requestAnimationFrame(() => {
    requestAnimationFrame(() => {
        try {
            window.print();
        } catch (e) {
            console.error('[pdfExport] window.print 抛错:', e);
            showToast('打印失败：' + (e && e.message ? e.message : '未知错误') + '，建议使用浏览器菜单的「网页转 PDF」', 5000);
        }
        // 兜底清理（部分浏览器 afterprint 不触发）
        setTimeout(cleanup, 1000);
    });
});
```

> [!NOTE]
> **为什么是双层 RAF？**
>
> - 第一层 RAF：将回调推迟到下一帧渲染前
> - 第二层 RAF：再推迟一帧，确保浏览器已完成 DOM 重排与样式应用
> - 双层 RAF 后再调用 `window.print()`，可保证打印快照基于最新 DOM 状态，且仍在用户手势上下文链上（RAF 是同步派发的，不会脱离手势）
